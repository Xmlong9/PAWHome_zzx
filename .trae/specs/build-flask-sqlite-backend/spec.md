# PawHome Flask 后端重构 Spec

## Why
当前项目以前端页面与本地 Mock 数据为主，缺少可持续演进的真实后端能力，导致认证、业务规则和数据一致性无法在服务端统一治理。需要建立基于 Flask + SQLite 的完整后端，打通前后端真实数据链路并支撑后续功能扩展。

## What Changes
- 对现有前端页面、交互流和数据依赖进行全面梳理，产出后端能力映射清单。
- 设计并实现 SQLite 数据库 Schema，覆盖用户、宠物、社区、服务、商城、订单、消息等核心域模型。
- 基于 Flask 开发 RESTful API，提供认证授权、标准 CRUD、分页查询、状态流转与业务校验能力。
- 建立统一的错误响应、输入校验、鉴权中间层与日志机制，保证接口一致性和可观测性。
- 将前端服务层从 Mock 切换为真实 API 调用，保留可配置降级机制用于开发调试。
- 补充端到端功能验证与关键接口测试，确保核心流程稳定可运行。

## Impact
- Affected specs: 用户认证、宠物档案管理、社区互动、服务预约、商城交易、订单履约、通知消息、个人中心
- Affected code: `backend/` Flask 应用与数据层、`miniprogram/services/` 接口服务层、相关页面的数据获取与提交逻辑、测试与配置文件

## ADDED Requirements
### Requirement: 前端能力盘点与后端映射
系统 SHALL 输出一份覆盖现有前端模块的后端能力映射，明确每个页面的实体、操作、接口和鉴权需求。

#### Scenario: 完整识别模块能力
- **WHEN** 对前端路由、页面状态和交互行为进行分析
- **THEN** 得到结构化的模块清单与后端支持点，并可追溯到对应页面

### Requirement: 统一数据模型与约束
系统 SHALL 在 SQLite 中建立规范化 Schema，并通过主键、外键、唯一约束与状态字段保障数据完整性。

#### Scenario: 写入与关联校验
- **WHEN** 创建或更新带有关联关系的业务数据
- **THEN** 数据库层和服务层共同保证关联有效、状态合法、重复写入受控

### Requirement: RESTful API 与认证授权
系统 SHALL 提供符合 REST 规范的 API，采用令牌机制实现身份认证，并按资源与操作粒度执行权限控制。

#### Scenario: 鉴权访问受保护资源
- **WHEN** 未认证请求访问受保护接口
- **THEN** 返回统一的未授权错误响应且不暴露内部实现细节

#### Scenario: 资源标准化操作
- **WHEN** 客户端对资源发起创建、查询、更新、删除请求
- **THEN** API 使用一致的路由语义、状态码和响应结构返回结果

### Requirement: 前后端真实数据联通
系统 SHALL 将前端原 Mock 数据入口切换为真实 API，并在失败场景下提供清晰错误反馈与可恢复策略。

#### Scenario: 页面请求真实后端
- **WHEN** 页面加载或用户提交表单触发数据操作
- **THEN** 服务层调用真实后端接口并驱动 UI 状态更新

#### Scenario: 请求失败处理
- **WHEN** 接口返回业务错误或网络异常
- **THEN** 页面展示可理解的错误信息并保持一致的重试或回滚行为

### Requirement: 可验证的系统稳定性
系统 SHALL 提供覆盖关键业务路径的测试与验证结果，包括认证、核心 CRUD、交易链路和异常分支。

#### Scenario: 执行回归验证
- **WHEN** 完成后端实现与前端对接
- **THEN** 核心流程测试通过，关键接口满足契约并可重复执行

## MODIFIED Requirements
### Requirement: 前端数据访问策略
前端数据访问 SHALL 以统一服务层为入口，默认使用真实后端 API；Mock 仅作为显式配置的开发兜底，不得作为生产默认数据源。

## REMOVED Requirements
### Requirement: 页面直接依赖本地静态 Mock 作为主数据源
**Reason**: 本地静态 Mock 无法覆盖认证、并发、权限与真实业务规则，阻碍系统级联调与上线可行性。  
**Migration**: 所有页面改由服务层请求 Flask API；保留可选 Mock 适配器用于离线开发与接口未完成阶段。
